## 〇、一句话

**回滚不是「把代码改回去」，而是「把线上正在跑的东西换成上一版能跑的产物」。**
代码在 git 里永远回得去；能不能在 1 分钟内让用户看到上一版，取决于**有没有提前存好那一版的产物**。

## 一、触发条件

### 1.1 分级（先判级别，再决定动不动手）

| 级别 | 判据 | 响应 |
|---|---|---|
| **S1 全线不可用** | 首页白屏 / 打不开，多数用户受影响 | 立刻回滚，边回滚边查 |
| **S2 核心链路断** | 打卡写入、列表读取持续失败（5xx 或大面积业务错码） | 立刻回滚，止血优先 |
| **S3 红线被破** | 危机入口 `/help` 打不开、热线号码错；错误页泄露 SQL/堆栈/内部字段；隐私数据外泄 | **最高优先，立即回滚**，不等定位 |
| **S4 数据被写坏** | 数据被错误覆盖/清空，且软删救不回 | 先回滚代码止血，再走数据恢复（§6） |
| **S5 体验回归** | 次要页面错位、文案错字、动效异常 | **不回滚**，前滚修复（见 §9） |

### 1.2 「什么情况必须回滚」判断表（余力加练）

| # | 线上现象 | 是否回滚 | 动作与理由 |
|---|---|---|---|
| 1 | 首页/子路由白屏，5 分钟内定位不到原因 | **必须** | S1。先回滚恢复可用，再在本地复现 |
| 2 | `/help` 打不开，或 12356 号码/拨号链接错 | **必须，立即** | S3 红线。这是产品不可破的底线，一秒都不能等 |
| 3 | 错误提示里出现 `RDB_ERR` / SQL / 英文堆栈 / 表名字段名 | **必须** | S3。泄露内部结构，且违背契约 §3 写死的口径 |
| 4 | 写入接口大面积 500，或返回 `INTERNAL` | **必须** | S2。用户写了没保存，比不能用更伤信任 |
| 5 | 读取列表返回空/字段 undefined（页面空白） | **必须** | S2。典型是字段名 camelCase 没对上，属发布引入的回归 |
| 6 | 同一天打卡出现多行、重复提交不去重 | **必须** | S4。数据正确性已受损，且会持续累积 |
| 7 | 删除后数据仍出现在列表 / 删除报成功但没删 | **必须** | S4。用户会认为「删了还在」，是隐私级问题 |
| 8 | 线上 bundle 名与本地产物不一致（部署没生效） | **不回滚** | 不是代码问题，重跑 §4 正确部署步骤即可 |
| 9 | 某个次要页面样式错位、错别字、动效卡顿 | **不回滚** | S5。回滚的代价大于收益，前滚改 |
| 10 | 新功能（如「提建议」）有问题但主流程正常 | **不回滚** | 摘掉入口或加开关，不必整站回退 |
| 11 | 接口变慢但没报错 | **不回滚** | 先观测，确认是发布引起再定 |
| 12 | 只是「感觉不对」但拿不出具体现象 | **不回滚** | 先按 §7 逐项验证，拿到证据再决策 |

> 判据核心：**回滚是为了「让用户马上恢复到能用的状态」，不是为了「让代码回到某个提交」**。凡是不能用「用户看到了什么」描述的故障，先验证再决策。

## 二、回滚前 10 秒确认（别跳过）

1. **回退点能不能构建？** 拿旧提交先在本地 `npm run build` 跑一遍。**提交顺序 ≠ 可回退顺序**——本次演练就撞到 `2e8c417` 是「一半提交」（`App.tsx` 引用了没提交的 `Fireflies.tsx`），构建直接 `TS2307` 失败。**没验过构建的提交，不许当回退点。** 已固化锚点标签 `rollback/v1.0-prev`（= 8399004，已验证可构建），回退直接用标签，不要裸哈希。
2. **回退点有没有产物备份？** 有 → 走 §4-A（最快）。没有 → 走 §4-B（重建，多花一次构建时间）。
3. **影响面**：这次回滚会让哪些**已上线的新功能**消失？要不要提前告知？
4. **数据要不要一起回滚？** 代码回滚**不会**回滚数据。如果故障写坏了数据，代码回滚只是止血，数据另走 §6。

## 四、静态托管回退步骤

### 4-A 用产物备份回退（推荐，最快）

前提：发版时按《发布清单》§5.1 存过 `dist` 快照。

```
# 假设备份在 %TEMP%\psyisle-v1.0-backup\dist
tcb hosting deploy "%TEMP%\psyisle-v1.0-backup\dist" \
  -e psyisle-prod-d9g109suw53257aed --verify
```

本次实测：**7 秒**（rc=0）。

### 4-B 用 git 重建旧版回退（没有产物备份时）

不要在主工作区 `git checkout` 旧提交（会打乱正在开发的工作区）。用 `git worktree` 在临时目录重建：

```
WT=%TEMP%\psyisle-rb
git worktree add "$WT" rollback/v1.0-prev   # 推荐用锚点标签，不要裸哈希
# 复用现有依赖（省去 npm install）：Windows 用 junction，不要复制
#   PowerShell: New-Item -ItemType Junction -Path "$WT\frontend\node_modules" `
#               -Target "C:\Users\24486\Desktop\工作台\心汐\frontend\node_modules" -Force
# 注意：worktree 里的 frontend/package.json 必须与已装依赖匹配，否则要先 npm install
cd "$WT/frontend" && npm run build
cd "$WT" && node scripts/spa-fallback.mjs      # build 会清空 dist，必须紧跟
tcb hosting deploy "$WT/frontend/dist" -e psyisle-prod-d9g109suw53257aed --verify
```

本次实测：构建 **7 秒** + fallback **~2 秒** + 部署 **8 秒**（rc=0）。
收尾：`git worktree remove "$WT" --force`（不清理会在 `git worktree list` 里留下脏记录）。

> 若回退点里 `App.tsx` 的顶层路由比当前少（本次 8 条 vs 当前 7+ 条），`spa-fallback.mjs` 会按该提交的 `App.tsx` 自动只补它有的路由——**不需要手改 ROUTES**。

## 五、云函数回退步骤（命令就绪，待真实演练）

云函数回退 = **用旧提交的函数代码重新部署**。

```
export MSYS_NO_PATHCONV=1                 # Git Bash 会把 /api/xxx 当本地路径改写
cd cloudfunctions/moods                   # 必须在函数目录内执行
tcb fn deploy moods -e psyisle-prod-d9g109suw53257aed \
  --force --deployMode zip --install-dependency true
```

**四条硬规则（每条都踩过）**

1. **`--force` 必加**：非 TTY 环境会卡在交互确认上，无限等待。
2. **不加 `--httpFn`**：会改函数类型，打断 HTTP 访问路径。函数类型（Event）建好就不能改，要改只能删了重建。
3. **一次只发一个函数**，并给 300 秒超时；连发两个会被默认 120 秒 SIGTERM 打断。
4. **必须在函数目录内跑**：在仓库根跑会把整个仓库（含 `node_modules`，约 140MB）打进包，`--dir` 拦不住。

**回退顺序**：先回退**被改动的那个函数**，不要一次全发。发完立刻 `curl /api/health` + 对应业务接口验证。

**演练步骤（接登录前必做，验证本手册不是纸上谈兵）**
1. 选回退目标函数提交：先 `git log --oneline -3 -- cloudfunctions/moods` 找到上一版；确认该提交函数可部署（函数无构建步骤，但需依赖一致）。
2. worktree 切到该提交 → 进函数目录 → `--force --deployMode zip --install-dependency true` 部署。
3. 验证：`curl /api/health` 与该函数业务接口（如 `GET /api/moods?limit=1`）正常。
4. **立刻回滚到当前版**（同样命令部署回当前函数源码），再验证一次，确认往返无误。
> 风险：旧函数若与当前 schema/校验不同，可能短暂改变写入行为；演练选低峰时段，且确保第 4 步能立刻回原版。

## 六、数据恢复（备查，本次不实操）

| 场景 | 手段 | 命令/位置 |
|---|---|---|
| 误软删（`is_deleted=true`） | PATCH 复位找回 | `PATCH /api/moods?id=<id>` body `{"note": "..."}` → 软删行可被编辑，复位即找回 |
| 单行被错误覆盖 | 用只读快照里的旧值 PATCH 回写 | `%TEMP%\psyisle-v1.0-backup\data\moods.json` |
| 整表被清 / 结构损坏 | 数据库实例快照回滚（PITR） | 腾讯云 PostgreSQL 控制台；**v1.0 未做实例级备份，这是已知缺口** |
| 演示数据重建 | 重跑 seed | `db/seed.sql`（结构见 `db/schema.sql`） |

**补全方案（上线前必做）**：当前 PostgreSQL 实例**未开 PITR / 自动备份** → 整表损坏只能靠 seed 重建演示数据。接登录前到腾讯云 PostgreSQL 控制台开启**自动备份 + 时间点恢复（PITR）**，并至少做一次全量备份验证可恢复。命令级的数据修复可用 `tcb db execute --sql "..."`（改 RLS/权限时加 `--role postgres`）。

> 铁律：**代码回滚 ≠ 数据回滚**。先判断故障有没有写坏数据；写坏了，代码止血后必须单独处理数据，否则回滚了个寂寞。

## 七、回滚后验证

**必须带缓存穿透**，否则你看到的是 CDN 上的旧页面，会误判「回滚成功」。

```
U=https://psyisle-prod-d9g109suw53257aed-1506897881.tcloudbaseapp.com

# ① 线上 index.html 引用的 bundle 名 —— 回退后应变成回退版的 bundle
curl -s -H "Cache-Control: no-cache" "$U/?t=$(date +%s)" | grep -o 'assets/[^"]*\.js'

# ② 该 bundle 能不能拿到
curl -s -o /dev/null -w "%{http_code} %{size_download}\n" "$U/assets/<回退版bundle>.js"

# ③ 每条子路由直开（不是从首页点进去）
for r in talk guide daily help breathe about suggest; do
  echo -n "/$r -> "; curl -s -o /dev/null -w "%{http_code}\n" "$U/$r/"

# ④ 接口仍正常
```

## 八、已知坑

1. **CDN 缓存会让你误判（本次真撞到）**：恢复 v1.0 后第一次截图，页面**白屏**，但服务器上文件是对的。原因是 CDN 边缘还在发旧的 `index.html`，指向了刚被覆盖掉的旧 bundle。**验证一律带 `-H "Cache-Control: no-cache"` 或 `?t=时间戳`；截图/给人演示前也加一次时间戳，别拿白屏当回滚失败。**
2. **静态托管部署是「覆盖上传」，不删远端多余文件**：回退到旧版后，新版多出来的子路由（如 `/suggest/`）和旧 bundle **仍然在远端可访问**。所以：
   - 好处——被回退掉的 asset 还在，浏览器缓存不会 404，回滚更安全；
   - 代价——**如果回滚的目的是让某个新功能下线，光部署旧版不够**，必须另外去托管控制台删掉多出来的文件，否则用户仍能直接输地址打开。
   - **本次实战（Day 26 补下线 `/guide/check`）：** 只删本地路由 + `spa-fallback` 入口不够——远端旧的 `guide/check/index.html` 仍会让该页面 200。必须显式删远端文件：
     `tcb hosting delete guide/check/index.html -e psyisle-prod-d9g109suw53257aed`（删目录加 `--dir`）。删完 `--verify` + `curl -H "Cache-Control: no-cache" /guide/check/` 确认 404。
3. **坏提交不能当回退点**：本次 `2e8c417` 构建失败（`TS2307` 缺 `Fireflies.tsx`，是并行会话 `git add -A` 造成的「一半提交」）。**回退前必须本地 build 验一遍**，并把「能构建」写进回退点清单。
4. **`npm run build` 会清空 `dist`**：必须紧跟 `node scripts/spa-fallback.mjs`，否则子路由直开 404。
5. **`worktree` 里的 `node_modules` 用 junction，不要复制**：复制 3000+ 文件很慢；junction 秒建。但前提是 `package.json` 依赖没变。
6. **别在主工作区 checkout 旧提交**：并行会话可能正在改文件，`checkout` 会把别人未提交的改动一起冲掉（本工作区已发生过多次）。一律用 worktree。
7. **云函数四坑**见 §5。

## 九、什么情况**不**该回滚

回滚是止血，不是治疗。以下情况前滚修复更快、代价更小：

- 只是样式/文案问题（S5）：改一版重新部署，比把整个站退回上一版更精准；
- 新功能局部有问题：摘入口 / 加开关，不必整站回退；
- 问题出在部署操作本身（漏 fallback、发的是旧产物）：**重跑正确步骤**即可，回滚反而多绕一圈；
- 已经定位到根因、且修复改动很小：直接前滚，避免「回滚—再发」两次发布窗口。

## 十、耗时基线（本次实测，可当承诺值）

| 操作 | 机器耗时 | 说明 |
|---|---|---|
| 构建旧版前端 | 7 s | `npm run build`（tsc + vite） |
| 补 fallback | ~2 s | `spa-fallback.mjs` |
| 部署到静态托管 | 7–8 s | `tcb hosting deploy --verify` |
| 回滚后验证（curl） | ~6 s | bundle + 子路由 + health |
| **静态托管回退（有产物备份）** | **~14 s** | 部署 + 验证 |
| **静态托管回退（需重建）** | **~23 s** | 构建 + fallback + 部署 + 验证 |
| **恢复回原版** | **~13 s** | 部署备份产物 + 验证 |
| 一次完整往返（含人工判断、截图取证） | **3–5 min** | 人参与的部分才是大头 |

> 结论：**机器侧 1 分钟内可完成一次回滚 + 恢复。真正的瓶颈是「判断要不要回滚」和「验证有没有回对」，不是命令本身。**
