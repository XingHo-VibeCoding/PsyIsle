## 四、意外与处理（这部分才是演练的价值）

### 意外 1：`2e8c417` 是「一半提交」，构建直接失败

- **现象**：`npm run build` 5 秒后报错
  ```
  src/App.tsx(13,23): error TS2307: Cannot find module './components/Fireflies'
  ```
- **原因**：该提交把 `App.tsx` 里新增的 `import Fireflies` 扫进了提交，但 `Fireflies.tsx` 本身没提交（直到 `a3e4b9f` 才补回）。典型的并行会话 `git add -A` 造成的「一半提交」坏仓库。
- **处理**：把回退点改为 `8399004`（上一个能构建的提交），重新构建通过。
- **沉淀**：**回退点必须本地 build 验一遍**，不能只看提交顺序。已写进《回滚手册》§2、§8。

### 意外 2：恢复后第一次截图是白屏

- **现象**：恢复 v1.0 后截图，页面**全白**，但 `curl` 拿到的 `index.html` 和 bundle 都是对的。
- **原因**：CDN 边缘还在发旧的 `index.html`（指向刚被覆盖掉的回退版 bundle），浏览器按旧引用加载不出来 → 白屏。
- **处理**：验证与截图统一加 `?v=时间戳`（或用 `Cache-Control: no-cache`），等 CDN 刷新后重拍即正常。
- **沉淀**：**回滚后验证必须穿透缓存**，否则会把「CDN 缓存」误判成「回滚失败」。已写进《回滚手册》§8 坑 1。

### 附带确认：静态托管部署**不删**远端多余文件

- 恢复 v1.0 之后，回退版的 `index-BwUlSeRX.js` 仍然 200 可访问。
- 含义有两面：好处是被回退掉的 asset 还在、浏览器缓存不 404；代价是**回退不会让新版新增的子路由（如 `/suggest/`）下线**，要下线得另外删文件。已写进《回滚手册》§8 坑 2。

## 五、结论：真出事敢不敢用这套流程？

**敢用在静态托管这一层，但要带着两个前提。**

- **敢的原因**：整个过程没有一处需要「改代码」，全部是把已存在的产物换上去；机器侧 36 秒往返，全程可回退（备份在手，恢复只是再部署一次）。这次不是照着手册抄，是真把线上搞成了旧版、再从旧版恢复回来，中间抓到两个真问题。
- **前提一：回退点必须先验构建。** 这次第一步就差点把坏提交当回退点。若真出事时慌着上，很可能推出一个编译不过的版本，故障从「功能坏了」变成「整站白屏」。
- **前提二：验证必须穿透 CDN 缓存。** 否则会把「缓存没刷新」误判成「回滚失败」，然后继续瞎折腾。
- **不敢用的部分**：云函数回退和数据恢复这次**没实操**，只有纸面步骤。这两条在真出事时能不能成，目前没有证据支撑——**下次演练必须覆盖云函数回退**，尤其是「函数类型不能改、一次只能发一个、非 TTY 必须 `--force`」这几条。
- **一句话**：前端回滚这条路径，现在可以当**可执行的应急预案**用；后端与数据两条，仍是**待验证的草稿**。
