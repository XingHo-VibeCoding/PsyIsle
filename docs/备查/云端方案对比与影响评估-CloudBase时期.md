## 0. 先摆一个前提：两个方案不是同一个赛道

| | 方案甲（现行） | 方案乙（新题面） |
|---|---|---|
| 一句话 | 一个**没有服务器**的网站 | 一个**有服务器**的网站 |
| 数据在哪 | 用户自己的浏览器里 | 我们的数据库里 |
| 谁负责保管 | 用户自己 | **我们** |
| 这不是技术选择 | **这是责任选择** | |

**为什么先说这个**：后面所有对比（工作量、成本、体验）都可以量化讨论，但**「谁来保管用户写的那些话」是不能只按技术优劣来选的一件事**。心屿的用户会在 F9 那个文本框里写下「我就是不行」这种话——这句话存在她自己手机里，和存在我们的数据库里，**是两件性质不同的事**。

## 1. 方案乙（云端全栈）的优势

**先说清楚：这一节我尽力把方案乙的好处说全，不掺水。**

### 1.1 优势清单

| # | 优势 | 具体是什么 | 对心屿的意义 |
|---|---|---|---|
| **1** | **跨设备可用** | 手机答完、电脑能看；换手机记录还在 | **这是方案乙唯一无法被方案甲替代的优势。** 也是 PRD 第 9 节自己写下的触发条件（≥ 20 人要求跨设备） |
| **2** | **用户真正拥有「长期记录」** | 情绪日记、多次测评的趋势对比（第一次 vs 半年后） | 本版明确不做的事（PRD 第 9 节），在方案乙里才有意义——**没有云端，跨会话长期记录本身就是不可靠的**，这是 PRD 自己给的理由（「必须靠导出/备份才能立住」） |
| **3** | **数据不因清缓存而丢** | 清浏览器数据、无痕模式、换浏览器都不影响 | 方案甲的三个真实软肋之一（PRD 第 8 节异常 1/2）**被彻底解决** |
| **4** | **可以知道有多少人在用** | 服务端能统计访问与功能使用 | ⚠️ 但 PRD 第 9 节把「数据统计 / 埋点」列为**永不做**（心理类产品的行为埋点涉及敏感隐私）。**这条优势要用的话，就得先推翻一个永不做项** |
| **5** | **能做的事不再受浏览器限制** | 服务端可以做全文搜索、内容审核、定时任务、AI 能力 | 心屿**目前没有任何功能需要这些**。属于「有了不亏，但现在用不上」 |
| **6** | **账号体系（可选）** | 微信登录 / 匿名登录，10+ 种方式 | 见 1.3 —— 这条是双刃剑 |
| **7** | **工程能力的学习价值** | 真实接触前后端分离、API 设计、数据库、环境变量、部署 | 对**「零基础学 vibe coding」这门课**而言，这是方案乙最大的实际价值：**方案甲几乎不产生「后端经验」** |
| **8** | **技术上是当前主流做法** | 前后端分离 + Serverless 是行业标准形态 | 简历/作品集角度更「正统」 |

### 1.2 一条容易被忽略的真实优势

**方案乙会强迫我们想清楚「数据模型」这件事。**

方案甲里，数据「长什么样」是随代码走的——`xinyu.abc.records` 里塞一个数组就完事，字段改了就是改了。方案乙要建表，**表结构一旦定下来，改动就要写迁移脚本**。这个约束不好受，但它会**逼出一个更清楚的数据设计**——而现在 PRD 第 7 节那 9 个 key 的设计，坦白说还停留在「够用」层面，没有经过建表级别的推敲。

### 1.3 一条必须单独说的优势（也是最大的陷阱）

**「加账号」在技术上让很多事变简单，但在心屿的定位上是自杀。**

- **技术视角**：有了登录，数据归属、跨设备、权限，全都顺理成章。
- **心屿视角**：PRD 第 1.3 节写得非常清楚——**「不用登录」是本站唯一没有被三个成熟产品覆盖的位置**。壹心理、简单心理、Calm **全部需要注册**，而 PRD 第 2.1 节的核心论证是「知道有资源的人很多，真正走进去的人极少」——**注册本身就是那道劝退门槛**。

> **判断（非数据证明）**：一个深夜情绪崩溃、还在犹豫「要不要承认自己有问题」的人，面对「请先注册」这四个字，大概率会关掉页面。**这一点是我认为方案乙最需要被质疑的地方**——它加进来的第一件事（账号），恰好会拆掉心屿唯一站得住的那条差异化。此判断待用真实用户行为验证。

## 2. 方案乙（云端全栈）的代价与风险

### 2.1 与 PRD 的正面冲突（不是「需要调整」，是「必须推翻」）

**这是本次对比里最硬的一条。以下冲突无法用「兼容处理」绕过：**

| # | PRD 原文位置 | PRD 写的 | 方案乙要求 | 冲突性质 |
|---|---|---|---|---|
| **1** | **第 5.0.4 节**（零基础九条硬约束，**可逐条 grep 检查**） | 不用框架 / 不用构建工具 / **无 `package.json`** / 不用 npm / 不引第三方库 / 每页 1 个 JS ≤ 200 行 / **不写异步逻辑** / 无后端 | **全部八条同时推翻**：React 是框架、Vite 是构建工具、必有 `package.json`、必有 npm 装依赖、云函数 SDK 是第三方库、组件化后行数远超 200、调 API 必写 `async/await` | **彻底推翻。** 这九条不是审美偏好，是 PRD 里「可检查」的验收项（第 10.2C 节逐条列出检查方法） |
| **2** | **第 10.2C 节**（零基础约束验收） | 7 条验收：无 `package.json`、无 `node_modules`、无 CDN、JS 里无 `async`/`await`/`Promise`/`fetch`、无 `<svg>`、每页 JS ≤ 200 行、**克隆到新电脑双击 `index.html` 即可运行** | 这 7 条**全部不通过** | **验收标准作废。** 尤其最后一条——云端方案**永远不可能**「双击就能跑」 |
| **3** | **第 9 节「本期不做」** | **用户注册 / 登录 = 永不做**，理由「数据只存 localStorage，这是差异化命门」 | 云端必须识别数据归属 → **必须有身份**（真实账号或匿名 ID） | **推翻「永不做」项。** 若用匿名登录可算折中，但账号体系的入口已经打开了 |
| **4** | **第 1.1 / 1.3 节（定位）** | 「不用登录、不花钱、打开就能用的心理学自助小站」；「不导流、不收费、不留人」 | 「打开就能用」变成「**先加载 → 可能要登录 → 才能用**」 | **定位表述需要整段重写。** 首屏那句「不用注册、完全免费、打开就能用」不再成立 |
| **5** | **第 8B 节「隐私」** | 不收集任何用户数据；**不发起任何对外请求**；所有内容只存 localStorage | 每一次答题都要发请求把数据传到服务器 | **隐私承诺反转。** 这是**从「我们看不到」变成「我们存着」**，不是同一件事 |
| **6** | **第 13 节风险表** | 「用户把测评结果当诊断」定为**高风险**，对策是不给分级、不给总分 | 数据一上云，**一次泄露就是全体用户的私密内容外泄** | **新增一类高风险**：数据安全责任，而 PRD 第 4.3 节明确排除「需要长期追踪病情的人」，我们也没有能力承接这类责任 |
| **7** | **F13 关于页验收** | 「明确写出『你的所有内容只存在你自己的浏览器里，**我们看不到，也收不到**』」 | 这句话**变成假话** | **必须整段改写。** 更麻烦的是：**用户是因为相信这句话才敢写真心话的** |
| **8** | **第 11.2 节（25 个单日任务）** | 25 个任务对 25 天，一天一个，**无缓冲** | 见 2.2 | **排期直接崩** |

### 2.2 排期影响：25 天装不下（这是算术，不是估计）

| 阶段 | 方案甲 | 方案乙需要额外做什么 | 额外天数 |
|---|---|---|---|
| **学基础** | 已会 HTML/CSS/JS | 学 React（组件、props、state、hooks）、Vite、npm、模块化、TypeScript 可选 | **+3~5 天** |
| **搭骨架** | T1 一天 | 初始化 Vite 项目、配路由、拆组件、配环境变量、本地起两个进程 | **+2 天** |
| **后端** | **无** | 建云环境、写云函数、连接数据库、写 SQL、配置数据权限、处理 CORS、调试 | **+4~6 天** |
| **数据模型** | 9 个 key 直接存 | 设计表结构、写建表 SQL、写迁移脚本、seed 数据 | **+1~2 天** |
| **认证** | **无** | 接匿名/真实登录、会话保持、过期处理、退出登录 | **+1~2 天** |
| **联调与异常** | T13b 一天（本地 try/catch） | 网络失败、超时、重试、离线、token 过期、并发写入冲突、服务端错误码……**每一类都要单独设计** | **+2~3 天** |
| **部署** | T22 一天（推 GitHub 即可） | 前端构建产物上传、云函数部署、环境变量配置、域名、HTTPS | **+1~2 天** |
| **合计额外** | — | — | **+14 ~ 22 天** |

> ⚠️ **我上一条消息说「+7~10 天」，现在看是低估了。** 那份估算是按「用最简单的云服务」算的；题面这套（React + Vite + 云函数 + PostgreSQL）是**完整的前后端分离架构**，额外工作量接近翻倍。
>
> **换算成人话**：现有路线 A 是 **25 天**，方案乙需要 **39~47 天**。要么砍掉大量功能，要么把课程排期整个拉长。

### 2.3 隐私责任：**这一条我认为需要单独决策，不能混在技术对比里**

| 维度 | 方案甲 | 方案乙 |
|---|---|---|
| 用户写的话存在哪 | **她自己手机里** | **我们的数据库里** |
| 我们能看到吗 | **不能**（连技术上都不可能） | **能**（而且在合规上说不过去的话，还不能说「我们不主动看」） |
| 泄露一次会怎样 | 只影响她一个人的手机 | **全体用户的私密内容外泄**，且**不可挽回、无法撤回** |
| 我们有没有能力保护 | **不需要保护**（没有可保护的东西） | **需要**：加密、权限、审计、防注入、备份、脱敏……而这是要专业团队做的 |
| 系统被黑会怎样 | 攻击者拿不到数据（服务器上根本没有） | 攻击者拿到**一份完整的、带情感内容的行为档案** |
| 用户受到的伤害 | 低（她自己本来就有这些数据） | **高，且不可逆**——心理困扰人群的隐私暴露可能直接造成伤害 |

**PRD 第 9 节列「AI 对话式情绪陪伴 = 永不做」时写的理由是「情绪类对话出错代价过大」——同一条逻辑在这里完全适用：情绪类数据泄露，代价同样过大。**

> **这一条不是「技术选型」，是「要不要承接这份责任」。** 我把它单独列出来，就是因为它不该被「Serverless 很省事」「按量计费很便宜」这类论据给冲淡。

### 2.4 成本（这块其实不是问题，但要说清）

**先说结论：成本不是决策因素。** 按腾讯云 CloudBase 官方价格测算：

| 项 | 官方单价（已核实） | 心屿量级估算 |
|---|---|---|
| **免费额度** | 每个账号可创建一个**免费体验版环境**，含 **3000 点/月**（1000 点 = 1 元，即 **约 3 元/月** 的额度） | **小规模完全够用** |
| 云函数调用 | 0.0133 元/万次 | 可忽略（量级太小） |
| PostgreSQL CPU | 0.342 元/(核·小时) | 低负载下共享实例按实际用 |
| PostgreSQL 容量 | 0.0005 元/(GB·小时) | 文本数据，几乎可忽略 |
| 静态托管流量 | 0.21 元/GB | 纯文本页面，可忽略 |
| 身份认证调用 | 0.5 元/万次 | 可忽略 |

**真实成本问题不在钱，在这三条：**

1. **免费环境不是永久的**：需要手动续期（每次 6 个月，到期前 1 个月内可续），**不支持自动续费**。一旦忘记续期 → **环境进入停服隔离期 → 未转付费即销毁**。**对一个「上线给大家用」的站点来说，这意味着必须有人记得续**，否则用户数据直接没了。
2. **免费环境不支持按量付费/加购**，超出 3000 点/月需要先升级付费套餐。
3. **一旦升级为付费，就有了持续支出与实名/计费配置**——而本项目目前**没有任何云账号**（无实名、无计费方式）。

### 2.5 还有一个副作用：开发体验变重

| 项 | 方案甲 | 方案乙 |
|---|---|---|
| 改一行看效果 | **双击 `index.html`**，秒开 | 起前端 dev server + 可能还要连云端环境，**首次配环境就是一道坎** |
| 断网能用吗 | **完全能用** | 前端能开，**功能全部不可用** |
| 能在手机上直接试吗 | 文件发过去就能开 | 需要先部署，或配内网穿透 |
| 出问题怎么查 | 看浏览器控制台 | **前端控制台 + 云函数日志 + 数据库，三处排查** |
| 「零基础」的门槛 | 会写 HTML 就能开始 | 要同时理解前端构建、后端运行时、数据库、网络请求、环境变量**五套概念** |

## 3. 一句话对撞：同一件事，两个方案的答案

| 用户会问的问题 | 方案甲的回答 | 方案乙的回答 |
|---|---|---|
| 「要注册吗？」 | 「不用，打开就能用」 | 「要么注册，要么给你分个匿名 ID」 |
| 「我写的东西谁看得到？」 | 「**只有你自己**，我们技术上做不到看」 | 「存在我们的数据库里，我们承诺不主动看」 |
| 「换手机数据还在吗？」 | **「不在」** ← 这是方案甲唯一的真短板 | 「在」 |
| 「清浏览器数据会丢吗？」 | **「会丢」** | 「不会丢」 |
| 「我现在就想用，要等多久？」 | 「**0 秒**」 | 「等页面加载完，可能还要登录」 |
| 「这站靠什么活着？」 | 「不导流、不收费、不留人」 | 「要付服务器钱、要有人维护续期」 |
| 「我深夜难受的时候它靠得住吗？」 | **「靠得住，连网都不用」** | 「网不好就打不开」 |

## 4. 我的三个中间判断（供你决策参考，不是结论）

### 判断 1：这两个方案可以并存，不必二选一

**方案乙最适合的位置不是「替换方案甲」，而是「PRD 第 9 节已经写好的 v2 路线」**——那一节自己就写了触发条件：「上线 30 天自然访问 ≥ 500 次且有 ≥ 20 人要求跨设备，才评估后端」。

**换句话说：方案乙要解决的问题（跨设备），恰恰需要先上线、先有用户，才知道是不是真问题。** 现在做，是在为一个**尚未被验证的需求**付出推翻 PRD 的代价。

> ⚠️ 但有一条要提醒：**如果现在就把架构改成云端，那「触发条件」这套逻辑就失效了**——因为那时候已经没有「纯本地版」可供对比和回退。

### 判断 2：如果这次是「课程作业需要一份云端设计」，那它和「项目要不要改路线」是两件事

我上一条消息提过这个可能，这里再说清：题面写的是「**示范路线可使用** React/Vite、CloudBase…」——**「可使用」是示例措辞**，不是「必须使用」。这门课 Day 5 的原始题面也是「技术路线有理由」，重点是**能不能说清取舍**，不是**必须选云端**。

**如果作业要的是一份云端设计文档**，那完全可以只**产出一份设计**（含项目结构、数据模型、API 列表、前后端数据流、错误处理、环境变量、迁移注意事项），**而项目本身继续走纯静态路线**。这样两个目的都达到，且不动 PRD。

### 判断 3：有一条「第三条路」值得考虑（如果你确实想要云端的一些好处）

| 折中方案 | 怎么做 | 得到什么 | 放弃什么 |
|---|---|---|---|
| **纯静态 + 可选导出/导入** | 加一个「导出我的数据」按钮，生成一个 JSON 文件；换设备时导入 | **跨设备**（手动，但管用）；**不丢数据**（用户自己保管备份） | 仍需手动操作；不能自动同步 |
| **纯静态 + 云同步作为「可选增强」** | 默认全本地；用户**主动**点「开启云同步」才登录 | 保住「不用登录就能用」；**愿意的人**才交数据 | 要维护两套数据路径（复杂度上升）；**不能上 CloudBase 免费额度**（见 2.4） |

**第三条路的核心理由**：**「导出/导入」是纯静态方案就能做到的跨设备方案**，代价只是用户多点两下。而它**完全不碰隐私责任、不推翻任何 PRD 约束、不增加排期**。在决定投入 14~22 天做云端之前，**我建议先评估这条能不能满足需求**。
