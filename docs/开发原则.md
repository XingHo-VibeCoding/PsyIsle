# 开发原则（心屿项目唯一源）

> 本文件是开发工作规则的唯一源（SSOT）。`AGENTS.md` 第 12 节只保留指向，不复制内容。
> 由老板提供的通用开发规则（2026-09-23）与项目裁定合并而成；规则之间冲突时，按优先级裁定：**保护用户 > 课程要求 > 开发效率**。

# 原则

做长期正确的事。

- 长期主义，面向维护，新增改动应降低未来开发成本，禁止引入技术债
- 警惕可能产生架构分叉的编码，按最佳实践来做统一的结构
- 单一真相源（SSOT），写入口唯一，其他皆派生、复用
- 结构性问题用重构解决，禁止补丁、特例绕过
- 遵循可执行最佳、现代的实践
- 积极引入成熟第三方库解决问题，而不是自己造轮子
- 优先阅读代码而非写代码，优先寻找项目内可用可扩展的代码
- 迭代修改而非增量修改，重写/重构后删旧代码
- 遵循 KISS 原则，选最短且长期最佳实现路径，架构导致冗余就简化架构
- 做合适程度的强类型，相同的类型也单一类型定义源
- 禁止做掩耳盗铃的事情，我们必须真实的做事
- 不需计算编码成本，AI 编码不是人工，永远选择最佳的方案
- 做深度封装的组件，将复杂度封装在组件内，只暴露很少的必要的生命周期和 API，要替调用方着想
- 少做短期主义的 hack 和补丁
- 精准手术刀式的修正，不做过度兜底

# 行为规范

## 开发前

- 先看代码，再询问信息和需求，不直接开发。
- 问完信息后设计方案，并等待人类确认后再开发。
- 采用强类型设计：前端用 TypeScript，同一类型只允许一个定义源。
- 除非特别要求，不做兼容，不保留历史包袱，面向长期干净整洁，减少复杂度。

## 开发中

- 采用 TDD，先编写测试，再实现功能，保证模块可进行有效单元测试，单元测试要涉及到下一层依赖，更深层的才可以 mock。
- 完成模块开发后要进行真实环境测试，使用真实资源模拟真实用户测试。
- 单文件超出 2000 行了必须进行结构审查，如果存在架构问题则按职责、层次、领域边界合理拆分。
- 注释只解释为什么（why），禁止复述做什么（what）。
- 不主动提法律诉讼、监管合规类提醒（未来统一合规处理）；但 `AGENTS.md` 第 9 节安全红线与第 13 节用户内容红线不属此类——它们保护的是弱势用户，任何情况下不放松。
- `.env`/凭据永不入库（本仓库是 Public，任何人都看得见）；提交前扫敏感信息，细则见 `AGENTS.md` 第 8 节。
- 及时删除无效代码，发现不符合原则或规范的代码顺手优化。
- 架构与基础组件的改进随功能开发顺手做，不设固定比例（心屿体量小，硬性比例会走向过度工程）。
- 修复 Bug 时禁止过度兜底，要定位根因，并用正确的逻辑解决问题。
- 不编写只有单一调用、没有复用或抽象价值的私有 Helper 函数。
- 保持代码始终可编译、可运行。
- 文档要保持索引和单一信息，不能复述已存在的逻辑——指向代码，而不是用文字复述一遍，避免形成分叉，避免浪费上下文。文档保持精简。**课程交付文档（PRD / 自检报告 / README）自包含优先**，索引化要求适用于 `docs/` 下与代码配套的文档。
- 产出保持 Stateless Deliverable（无状态交付）：每次修改都保持产物直接可交付，不包含版本补丁说明与修改过程描述，产品和代码中不包含修改说明。课程要求的 Day N 标注不算修改说明。

## 开发后

- 每完成一个独立、可回滚的变更，经人类允许并完成 Code Review 后再 Git Commit；课程每日收尾指令「提交并推送」视为人类事先允许，不再逐次确认。
- Commit 信息按课程约定：标题「Day N｜一句话」，正文两行（改了什么 / 加了什么）。
- 每次 Commit 都必须保证代码可编译、可运行。
- 全量测试只在部署上线前运行（平时不跑，缩短开发时间）；**涉及危机页、测评提交、用户数据读写的改动，部署前全量测试通过是硬门槛**——本产品部署即上线，没有预发环境。
- 开发完成后，功能一切正常后，再审一遍代码：看是否有架构分叉、职责不清、历史包袱、过度实现和过度兜底、没有复用价值的 helper（合并之）、无用的修改说明，保持长期干净清晰的架构。
